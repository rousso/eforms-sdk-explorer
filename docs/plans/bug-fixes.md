# Plan: bug-fix pass

## Context

While building the SDK 2 support (`sdk2-support.md`), the planning and implementation sessions recorded defects in code they read but were not asked to change. This plan collects the ones confirmed in the code of branch `claude/zealous-feynman-uuwemi` at commit f990023, so they are fixed before the TED design-system restyle, which touches the same templates and stylesheets. The two open upstream bug reports (OP-TED/eforms-sdk-explorer #56 and #57, Codelists tab) are not part of this plan: they could not be reproduced on this branch (1.16.0-rc.5 vs 1.15.1: 11 modified codelists, exactly the 11 with content changes; the `country` filter shows its 5 codelists), and the user will close them upstream after the merge if that stays so.

Working method, as for the SDK 2 plan: one fresh implementation session (Opus 5.5, effort xhigh) on branch `claude/zealous-feynman-uuwemi`, opened with the prompt in `README.md` of this folder; one commit per item below, in the given order; `npm run smoke` before each push; a dated entry in Progress at the end. Rules: the repository's own style (ES modules, one `TabController` subclass per tab, web components, jQuery and Bootstrap 4), object-oriented clean code, no helper grab-bags, no change beyond the item. Questions go to the planning session, not the user.

## Items

### 1. `CustomError` throws instead of reporting the wrapped error
- File: `src/js/custom-error.js`.
- Symptom: when the second constructor argument is a string or another `CustomError`, the constructor calls `this.formatDetail(...)` inside the `super(...)` expression, before `super()` has run, which throws a `ReferenceError`. Every tab wraps errors this way (`new CustomError(ERROR_GENERATING_OVERVIEW, error)`), so the user gets a script error instead of the message. `AjaxError` inherits the problem for the same inputs.
- Fix: compute the message before calling `super()`; make `formatDetail` a static method (it uses no instance state) and call it as such. Keep the three cases and the resulting messages exactly as intended today.
- Verify: a Node check (throwaway or kept under `scripts/`, the implementer's choice) that constructs `CustomError` and `AjaxError` with a string, a `CustomError`, an `AjaxError`, a jqXHR-like object and `undefined`, and asserts the messages; in the browser, a forced failure in a tab shows the toast with the detail, not a console `ReferenceError`.

### 2. View Templates diff is never cleared
- File: `src/js/tabs/view-templates-tab.js` (`#diffContainer()` returns `#view-templates-diff`), `index.html` (the element is `#view-template-diff`, the id `injectTextDiff` is given).
- Symptom: `deactivated()` and `#switchToOverview()` empty an element that does not exist, so the last diff stays in the DOM (memory) and the diff2html scroll listeners stay attached to it.
- Fix: one id for both, following the other tabs' naming (`#view-templates-diff`); update `index.html` and the `injectTextDiff` call.
- Verify: after Compare and back to Overview, `#view-templates-diff` is empty; smoke check.

### 3. Card-group filter keeps values from the previous comparison
- File: `src/js/components/card-group.js` (`empty()` resets `indexCards` and the container but not `filterValues` or the nav), used by every card tab after a version change.
- Symptom: after changing versions, the left filter column keeps entries from the previous pair (and `appendCard` will not re-add an existing value, so entries can also be missing from the nav after a `dispose()`/`empty()` sequence). `ValidationTab` works around it by calling `dispose()`.
- Fix: `empty()` clears the cards, the filter values and the rendered filter options, and restores the `(all)` selection, so that a tab can rebuild from nothing; keep `dispose()` for releasing the component. Remove the workaround in `ValidationTab` if `empty()` now suffices.
- Verify: Codelists 1.15.1 vs 1.14.2 then 2.0.0-alpha.4 vs 2.0.0-alpha.3: the filter column lists only the second pair's parents; smoke check.

### 4. Error toast replays old messages, and the version-list error loses its detail
- File: `src/js/app.js` (`clearApiStatus()`, `updateApiStatus()`, `populateDropdown()`).
- Symptom: `clearApiStatus()` empties the toast body but not `apiStatusMessage`, so the next error shows the previous messages again until the 15-second timeout resets them. `populateDropdown()` catches every error and reports the fixed text "API call failed to fetch tags." (with a stray second argument), discarding the message `SdkRepository` built (`ERROR_FETCHING_VERSIONS` with the detail).
- Fix: `clearApiStatus()` also resets `apiStatusMessage` and the pending timeout; `populateDropdown()` reports `error.message`.
- Verify: trigger two errors with a tab change between them; the toast shows only the second. Simulate a failing versions request; the toast names the versions list.

### 5. A tab keeps the previous comparison on screen when its load fails
- Files: the tabs' `fetchAndRender*` methods (`src/js/tabs/*.js`), possibly `TabController`.
- Symptom: when fetching or rendering fails (toast shown), the tree or cards of the previous pair stay visible under the new version selection, which reads as if they belonged to it.
- Fix: each tab clears its own content (tree, card group, diff, alerts) before fetching, in `fetchAndRender()`, so a failure leaves an empty pane plus the toast. Do this in the tabs, not with a generic hook, unless a clean override point in `TabController` (e.g. a `clear()` called by `activated()`/`versionChanged()` before `fetchAndRender()`) reads better; decide by what is clearer in the code.
- Verify: select a pair, then force a failure (a version whose file is missing, e.g. fwd mode with a faked 500); the pane is empty and the toast names the file; smoke check for one tab.

### 6. Schematrons overview ignores cancellation
- File: `src/js/tabs/schematrons-tab.js` (`fetchAndRenderOverview`).
- Symptom: the per-card `setTimeout` lacks the `if (!this.aborting)` guard the other card tabs have, so a load abandoned by a tab switch keeps appending cards.
- Fix: add the guard, as in `SchemasTab`.
- Verify: switch away from Schematrons while it loads; no cards appear afterwards (observable in the smoke run by counting cards after a quick switch).

### 7. Component stylesheets drift from the page
- Files: `src/js/components/bootstrap-web-component.js` (`requiredCss()`: Bootstrap 4.5.2 from stackpath.bootstrapcdn.com), `src/js/components/tree-detail-split-view.js` (jsTree theme 3.2.1 from cdnjs), `index.html` (Bootstrap 4.6.2 from jsDelivr, jsTree 3.3.12 from cdnjs).
- Symptom: three CDN hosts and two version pairs for the same libraries; the shadow roots render with an older Bootstrap than the page.
- Fix: one place holds the library URLs (e.g. `appConfig.stylesheets` with `bootstrap` and `jstreeTheme`), used by `index.html` through nothing (it stays static) and by the components; same versions as the page (4.6.2, 3.3.12), same hosts.
- Verify: no stylesheet request to stackpath or to the old versions in the smoke run's request log; the page looks the same.

### 8. `deactivated()` disposes nothing
- File: `src/js/tabs/tab-controller.js` (`$(this.#id).tab('dispose')`).
- Symptom: the selector lacks `#`, so the call matches nothing; disposing the Bootstrap tab was never needed (the tab is re-shown later).
- Fix: remove the call.
- Verify: tabs still switch; smoke run unchanged.

### 9. Property values are injected as HTML
- File: `src/js/components/property-card.js` (`render()` sets `innerHTML` from the property values; `#formatPropertyValue` turns objects into JSON with `<br>` and `&nbsp;`).
- Symptom: an SDK text value containing `<` or `&` is parsed as HTML and can break the card.
- Fix: render text values with `textContent`; keep the formatted-JSON path for objects, but escape the JSON text before inserting the line breaks (or render JSON into a `<pre>`-styled element with `textContent`, which removes the `<br>`/`&nbsp;` replacements). Choose the one that keeps today's look.
- Verify: a property value `a < b & c` renders literally in the details pane; JSON values keep their indentation.

### 10. Codelists compares a renamed codelist under the wrong filename
- File: `src/js/tabs/codelists-tab.js` (`#createIndexCard`, `#checkForChanges`, `fetchAndRenderDiffView`).
- Symptom: for a codelist present in both versions, the tab fetched both versions' files under the filename of the main version's index entry (`diffEntry.get('filename')`). Up to 1.11.0, tailored codelists have their parent in the filename (`criterion_exclusion-ground.gc`), from 1.12.0 not (`exclusion-ground.gc`), so a comparison across 1.12.0 requested a file that one version does not have: a 404, an error toast and a card that never gets a status (one codelist, `exclusion-ground`, for 2.0.0-alpha.4 vs 1.9.0). Found while implementing item 3; part of upstream #56 for such comparisons.
- Fix: each version's file by that version's own index entry (`diffEntry.mainItem.filename` for the target, `diffEntry.baseItem.filename` for the base), for the background status check and for Compare; the diff's title is the target's filename. A codelist in one version only keeps its one filename.
- Verify: Codelists 2.0.0-alpha.4 vs 1.9.0 shows no error toast and every codelist gets a status, `exclusion-ground` among them; Compare on it fetches `exclusion-ground.gc` from 2.0.0-alpha.4 and `criterion_exclusion-ground.gc` from 1.9.0; smoke check.

### 11. Filters ignore the cards whose status is still being checked
- File: `src/js/components/card-group.js` (`appendCard`).
- Symptom: `appendCard` gave a card its display rule only once the card had a status; a card whose status is checked in the background ignored both the property filter and the status filter until its check finished, and for good if the check failed. In the Codelists tab (about 270 files checked in each version) this lasts a while: for 1.16.0-rc.5 vs 1.15.1, "country" clicked during the load left 251 cards visible, 246 of them not country codelists, and the status "modified" left 241 visible, 239 of them not yet checked. This explains upstream #57 ("Filter by parent codelist": clicking "country" has no effect) and #56 (added/removed/modified detection "does not appear to work"); found while reading them.
- Fix: a pending card gets, as soon as it is appended, the display `var(--filter-<value>-all, var(--filter-all-all, none))`: shown only when the status filter is "all" and the property filter matches it (or is "(all)"); the `statusChanged` listener replaces it with the known-status rule as before. A card whose check fails stays pending (shown under "all", hidden under a specific status) and keeps today's toast; no new status.
- Verify: Codelists 1.16.0-rc.5 vs 1.15.1, "country" clicked while the checks are still running: only country codelists are visible then, and exactly its 5 after the checks; "modified" selected while loading: no pending card is visible, and exactly the 11 modified after the checks; smoke checks.

### 12. Version changes: clear first, never apply stale results, no lost changes during start-up
- File: `src/js/app.js` (`init()`, `versionChanged()`, the tab probing); also `src/js/tabs/validation-tab.js` (`#probeRules`), see the fix. From the external review of PR #1 (findings A1–A3).
- Symptom: (A1) `versionChanged()` probed the tabs before the active tab's `versionChanged()`; when a probe failed (for example a 500 on `validation/rules.efx`), the toast showed and the tab never cleared, so the previous comparison stayed under the new selection. (A2) Two quick version changes could apply the older probe's answer after the newer one, leaving the tab bar wrong for the selected pair. (A3) The dropdown and tab handlers were attached in `init()` only after the start-up probe, so a dropdown change made during it was lost (the dropdown showed one version, `appState` and the tabs another).
- Fix: `versionChanged()` cancels the active tab's requests and clears it first; a private selection counter (`#selection`) is incremented by every selection, and after the probes' wait a superseded selection stops (no tab-bar change, no Home activation, no render, no toast); `init()` attaches the handlers right after `populateDropdown()`, and the start-up probe takes the same guarded path (`#updateForSelection`). Because the active tab's requests are now cancelled at the start of a version change, the `rules.efx` probe goes through `SdkExplorerApplication.ajaxRequest` instead of the Validation tab's: it answers which tabs apply to a version and is shared, as a cached promise, by the questions of several selections, so an abort by the tab would have handed the next selection an aborted probe.
- Verify: a failed probe leaves the Fields pane empty with the toast; a probe held for an older selection and released after a newer one does not change the tab bar; a version change made while the start-up probe is held ends with the dropdown, `appState` and the tab bar agreeing; smoke checks.

### 13. CardGroup keeps its controls and its selections in step
- File: `src/js/components/card-group.js` (`empty()`, `render()`). From the external review of PR #1 (finding A4).
- Symptom: setting `filter-property` (the Validation source switch) re-renders the shadow DOM: the status `<select>` shows "all" and the cards container is back to `--filter-all-all: block`, but `selectedStatusFilterValue` kept the previous value ("modified"), so the next folder click set `--filter-static-modified` next to `--filter-all-all` and the cards shown matched neither the controls nor the selection (all 574 schematrons for "static" between the two alphas).
- Fix: emptying a card group resets its filters: `empty()` sets both selections back ("(all)", "all"), and the new `#showSelectedFilters()` makes the controls and the cards follow the stored selections (the status select's value, the highlighted property link, and the one `--filter-<value>-<status>` variable on the container); `render()` calls it, so a re-render never desynchronises controls and state.
- Verify: under EFX rules select "modified" (no card shown), switch to Schematron: the status shows "all" and all cards are visible; select the folder "static": only the static cards, whatever their status; smoke checks.

### 14. A superseded load cannot overwrite a newer comparison
- Files: `src/js/tabs/tab-controller.js`, and the seven card tabs (Codelists, Notice Types, Schemas, Schematrons, Translations, Validation, View Templates). From the external review of PR #1 (finding B1, pre-existing).
- Symptom: `TabController.versionChanged()` did not cancel the previous load, so a slow response for the old pair could render after the new pair's tree and replace it while the dropdown showed the new pair. The cards of a load are added in deferred `setTimeout`s, which cancelling the requests did not reach (their `aborting` guard only changed on tab switches): after a version change made while a load was adding its cards, the rest of them were added to the newer comparison's pane (256 of 257 for Codelists 1.3.6 vs 1.3.2), until the new load's own index arrived and emptied it. The background status checks go through `ajaxRequest`, so cancelling covers them.
- Fix: `versionChanged()` calls `cancelRequests()` before `clear()`, as `deactivated()` does. `TabController.defer(work)` runs a piece of rendering in a timeout and tracks it like a request; `cancelRequests()` also drops the deferred work that has not run yet, so a cancelled load (version change, tab switch, source switch) renders nothing afterwards. The seven card tabs add their cards through `defer()`; the `aborting` flag, which nothing read any more, is removed.
- Verify: a held `fields.json` of a first pair, released after a second pair is shown, leaves the second pair's tree; a version change made as soon as the first Codelists card appears, with the newer pair's index held, leaves an empty pane until that index arrives and no duplicate card afterwards; smoke checks.

### 15. Tree labels are text, not HTML
- File: `src/js/components/tree-detail-split-view.js` (the jsTree configuration). From the external review of PR #1 (finding B2, pre-existing).
- Symptom: jsTree parsed the tree-node texts (SDK names and ids) as HTML, so a name containing markup was rendered as markup (`<b>x</b>` became a bold "x").
- Fix: `core.force_text: true`. The root headings of fwd mode are plain text and render as before.
- Verify: a field name faked to `<b>x</b> NUTS code` is shown as it is, with no element in its label; smoke check.
